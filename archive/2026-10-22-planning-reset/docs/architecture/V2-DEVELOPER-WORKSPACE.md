# V2 开发者工作区：MCP、钩子、worktree 与 Git 树

日期：2026-10-22。状态：**已确认的 V2 功能要求，尚未实现。** 本文补充 [V2 架构](V2-ARCHITECTURE.md) 与 [V2 实施计划](../plans/AGENT-V2-REBUILD.md)，不新增独立服务或执行引擎。

产品形态保持为手机 App、电脑 Agent 两个入口，共用一套 Rust 核心。手机可以查看和操作已连接电脑的开发工作区；电脑宿主负责当地的命令、Git、worktree 和脚本进程。

## 1. 四项能力的归属

| 能力 | 用户能做什么 | 所属模块 | 当前项目基线 |
| --- | --- | --- | --- |
| MCP | 配置服务、发现并调用工具、读取服务资源，把结果用于任务 | 核心工具目录 + MCP 连接适配 | 已有 HTTP/stdio 连接、工具调用与文档资源读取，V2 需迁入 Rust |
| Agent 钩子 | 在任务或工具的关键节点执行用户配置的检查、脚本或通知 | Rust 任务核心的事件点 + 设备宿主的钩子执行器 | 尚无面向用户的完整 Agent 钩子能力 |
| Git worktree | 为修改代码的任务建立独立工作区和分支，查看、保留与清理它们 | 电脑宿主的仓库管理能力 | 仓库开发中使用 worktree 不等于应用已实现管理功能 |
| Git 树 | 查看文件树与修改状态、分支/提交关系图、worktree 与任务关联、差异 | Flutter 代码工作区 + 电脑宿主的结构化 Git 查询与 CLI | 现有科研终端可执行命令，但没有完整 Git 图形工作区 |

当前 `.githooks/pre-commit` 是本仓库开发流程里的 Git 钩子，不是产品内的 Agent 钩子。

## 2. MCP 首版范围

- 电脑端支持 stdio 本机 MCP 进程和 HTTP MCP 服务；手机直接使用可访问的 HTTP MCP 服务，也能发起使用电脑本地 MCP 的电脑任务。
- 对本机进程依赖 Node/Python 等运行时的服务，由实际有该运行环境的电脑宿主管理；不假定手机可以直接运行同一条桌面启动命令。
- 支持协议/能力协商、工具发现、工具调用、资源读取、错误和取消；保留现有文档 MCP 场景。额外协议能力按服务声明和实际需求接入。
- 工具结果和图片观察进入原有任务循环；MCP 连接、钩子和 Git 工具都归同一个任务记录与取消机制。
- 配置标明服务所在设备、所需运行环境和凭据引用，模型只能看到当前任务选定的能力。

MCP 定义工具与上下文接入机制，具体工具执行环境仍由宿主提供。[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)。

## 3. Agent 钩子与 Git 钩子

### Agent 钩子

首期提供下面五个固定事件点。事件名称是本应用规划，不表示已经兼容其他 Agent 产品的配置格式。

| 事件点 | 时机 | 典型用途与结果 |
| --- | --- | --- |
| 任务开始 | 目标设备、仓库和 worktree 已就绪 | 准备依赖、检查工作区；失败可阻止任务开始 |
| 工具执行前 | 即将执行已确定参数的工具动作 | 检查规则并允许/阻止该动作 |
| 工具执行后 | 工具结果已返回 | 格式化、补充验证、记录信息；脚本改动后的状态需要重新读取 |
| 任务验收前 | 即将判定成功 | 运行测试或质量检查；未通过就不能把任务标为成功 |
| 任务结束 | 任务已产生明确终态 | 通知与归档；记录失败信息，不自动递归启动同一个任务 |

首版配置仅需事件、过滤条件、命令与参数、超时和失败处理。使用固定顺序的处理器列表，不建设通用规则语言或工作流平台。

钩子在任务实际执行设备上运行；仓库任务的工作目录固定到该任务的 worktree，其他任务使用其明确配置的工作目录。电脑支持用户配置的命令脚本；Android 钩子使用宿主已支持的动作/回调，不能把桌面 shell 脚本误当成手机通用能力。

钩子与普通工具共用超时、取消、输出限额和过程记录。前置检查失败阻止后续动作，后置失败如实记录，已执行动作不伪装成未执行。结果未知时不自动重跑脚本；重连显示历史事件也不重复执行钩子。不会把钩子调用再次送入相同事件点形成递归。

用户级配置可直接管理；项目附带的脚本配置须由用户为该项目启用。配置变更不应借助模型输出自动提升执行权限。工具与钩子共用任务的设备、工作区和授权范围。

### Git 原生钩子

`pre-commit`、`commit-msg` 等由 Git 操作触发，按照仓库实际的 `.git/hooks` 或 `core.hooksPath` 配置处理。Agent 不再额外调用一次同名钩子，也不在失败后默认加 `--no-verify` 绕过检查。

导入仓库时需要识别其实际钩子配置并由用户选择是否信任。涉及 checkout/worktree/commit 等可能触发脚本的操作，遵守这一选择；不得因创建了新 worktree 就假定脚本来源已可信。

Git 钩子与 Agent 钩子在 UI 中分别展示触发来源和执行结果，避免同一项检查被重复注册到两个机制中。[Git 钩子说明](https://git-scm.com/docs/githooks)。

## 4. Worktree 的用户流程

1. 选择已连接电脑及其仓库、基准提交/分支。
2. 修改代码的任务默认新建独立 worktree 和任务分支；只读分析可以直接使用选定工作区。
3. 任务绑定仓库身份、worktree、分支和基准提交；后续文件操作、命令及钩子沿用该上下文。访问仓库的 MCP 工具须能明确指定目标 worktree；远程服务自身的权限和文件路径不由客户端工作目录自动约束。
4. 完成后查看差异、测试与钩子结果，用户决定保留改动、提交或合并。
5. 清理只针对本任务创建的 worktree；存在未提交修改或需要保留的提交时先展示处置选择，不自动强制删除。

必须处理的实际边界：

- 原工作区存在用户未提交修改时，新任务默认从明确的提交建立 worktree；需要包含未提交内容时显式选择并传递相应改动，不自动复制整个目录、密钥或忽略文件。
- 同一个 worktree 首期只允许一个活动写任务；并行修改任务使用各自分支与 worktree。
- 任务失败或取消后，保留已经产生的修改供查看；任务重试不会重新创建同名分支并覆盖原结果。
- 用户在外部 Git 工具中改变分支或 worktree 状态时，应用刷新并说明变化，不自动 reset 用户工作区。
- 合并和冲突解决属于明确的仓库操作；不得把“模型说已完成”直接解释为自动合并或推送授权。

worktree 是同一仓库的多个工作目录，共享部分 Git 数据；它提供工作区隔离，不等于操作系统沙箱。[Git worktree 文档](https://git-scm.com/docs/git-worktree)。

## 5. Git 树的具体交付

“Git 树”按以下三个相互关联的视图实现：

| 视图 | 首版显示内容 | 用户操作 |
| --- | --- | --- |
| 文件树与变更 | 目录、已修改/新增/删除/未跟踪文件、暂存与未暂存状态 | 查看文件和差异、选择暂存/取消暂存、审阅后提交 |
| 分支与提交图 | 提交节点、父子关系、分支/标签、HEAD、合并关系 | 浏览历史、选择提交/分支、比较差异 |
| Worktree 与任务 | 工作区路径、分支、关联任务、当前状态、未提交改动 | 打开任务、查看结果、保留或清理本任务工作区 |

手机界面呈现从电脑查询到的结构化状态；Git 命令和修改发生在电脑上。查看远程仓库不要求把完整仓库克隆到手机。手机本地完整 Git 运行环境另行评估，不作为远程 Git 工作区的隐含前置条件。

电脑宿主优先调用本机 Git CLI，保持 worktree 和原生钩子语义。输出转换为文件状态、提交及父节点、引用和 worktree 记录，Flutter 据此绘制界面；不靠解析彩色终端图或截图充当提交图。CLI 可以展示文本提交图和同一份工作区状态。

基本历史和分支图按需加载；浅克隆或历史尚未加载完整时明确标记。暂存、提交、分支与合并操作完成后回读 Git 状态，再更新 UI。

## 6. 一条完整验收流程

```mermaid
flowchart LR
  A[手机选电脑与仓库] --> B[建立任务 worktree]
  B --> C[任务开始钩子]
  C --> D[模型调用内置 / MCP 工具]
  D --> E[工具前后钩子与结果回读]
  E --> F[验收钩子 / 测试]
  F --> G[展示文件差异与 Git 提交图]
  G --> H[用户决定提交 / 合并 / 保留]
```

这一流程属于同一个电脑任务：同一任务 ID、同一工作区绑定、同一套日志和取消入口。手机断连后由电脑持有执行；重连恢复图形视图与任务状态，不重新触发钩子或重建 worktree。

## 8. 必须有的验收证据

- HTTP MCP 和桌面 stdio MCP 各至少一个真实测试服务，验证发现、调用、资源和取消；旧文档 MCP 用例继续通过。
- Agent 钩子正常执行、前置阻止、超时、失败、取消均可见；禁止动作未执行；任务重连不会重跑已完成钩子。
- Git `pre-commit` 拒绝一次测试提交时，应用如实报告且没有绕过；Agent 钩子与 Git 钩子的运行次数符合各自触发条件。
- 两个修改任务使用不同 worktree；原工作区的未提交文件保持原样；脏工作区清理不会被默认强制执行。
- 用包含分支和合并的测试仓库核对提交图、父节点、HEAD、文件状态及差异；外部 Git 操作后界面可以刷新到真实状态。
- 手机发起工作区任务、断连重连、查看结果并审阅提交的完整流程有设备端记录。

本轮只更新需求和规划，没有创建工作树、运行用户钩子、提交或修改仓库历史，也未把上述计划标作现有应用能力。
