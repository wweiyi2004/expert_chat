# V2 整体重构计划

日期：2026-10-22。状态：**当前主规划，所有实现阶段尚未开始。** 本轮交付为规划更新，不代表已建立 Rust、Android Agent 或 V2 应用工程。架构见 [V2 模块设计](../architecture/V2-ARCHITECTURE.md)。

MCP、钩子、worktree 与 Git 树已列入必做范围，详细交互、模块归属和验收见 [开发者工作区](../architecture/V2-DEVELOPER-WORKSPACE.md)。

## 1. 方案变化

| 项目 | 原增量方案 | V2 主规划 |
| --- | --- | --- |
| 起点 | 先从聊天控制器抽出 Dart 任务层 | 先验证两端能否使用同一 Rust 核心 |
| 执行逻辑 | 手机 Dart、电脑 Rust，后期考虑统一 | Rust 一套逻辑、两端各自运行实例 |
| 手机平台能力 | Kotlin 执行器经 Dart 注册 | Kotlin 宿主持有核心并提供执行器；Flutter 作为工作区客户端 |
| 旧代码用途 | 以逐批搬迁现有模块为主 | 作为功能、数据和行为基线；符合新接口的实现可复用 |
| 兼容验证 | 跟随每次旧工程变更 | 独立 V2 验证，再进行数据导入和业务覆盖验收 |
| 目录 | 原工程内逐步归口 | 独立 `v2/` 工程验证，新旧版本并行核对，验收后切换 |

原方案仍有价值的部分是职责划分、真实错误处理、数据所有权和验收场景。原来的 P1–P6 不再是主执行顺序；本计划使用 V0–V5，避免两份路线图同时生效。

## 2. 先建立旧版功能基线

从当前工作区记录实际能力和数据样本，按三类管理：

1. **V2 主链必须具备**：多协议聊天、工具循环、MCP、Agent 钩子、任务 worktree、Git 文件状态树与分支提交图、任务取消、持久记录、Android 操作、电脑命令与远程任务。
2. **正式替代旧版前迁入**：语音、资料/项目/记忆、学习、创作、科研终端、备份、设置及更新等已有产品能力。
3. **单独决策的兼容项**：旧 Gateway/AuthService、实验 Web 工程，以及非 Android/Windows 平台的发布范围。

每项写清用户场景、旧版表现、预期的新行为和验收证据。已知 bug 不列为必须兼容的行为；没有明确决定移除的现有功能，不得因新版本能演示 Agent 就被默认删掉。

## 3. 阶段与交付门槛

| 阶段 | 用户可感知的交付 | 前置条件 | 退出条件 |
| --- | --- | --- | --- |
| **V0 技术贯通** | 同一 Rust 核心可从 Android 和电脑启动，流式结果可见且可停止 | 功能基线与最小任务定义 | 真机桥接、取消、回调与生命周期通过；决定采用该架构 |
| **V1 核心任务闭环** | 电脑 CLI 在任务 worktree 中调用内置/MCP 工具，运行钩子并返回差异 | V0 | 任务独立运行；MCP、钩子、工作区隔离与 Git 状态可验收 |
| **V2 Android 操作** | 在两个演示 App 中完成可核验的跨 App 任务 | V1 | 点击/输入/滚动/跳转、权限与停止场景通过真机验证 |
| **V3 远程电脑** | 手机发起任务、查看 worktree、文件变更与分支提交图，断连后可恢复 | V1；V0 的手机任务客户端 | 配对、任务续传、取消确认、Git 视图与基本暂存/提交闭环 |
| **V4 产品与数据迁入** | 原有主要工作区和四协议能力在 V2 可用 | V1；按需依赖 V2/V3 | 功能覆盖表、配置/备份导入、两端一致性和性能对照通过 |
| **V5 试用与切换** | 可安装、可恢复数据、可持续使用的 Android + Windows 版本 | V2/V3/V4 | 真实设备和完整场景验收、回退演练、已知限制记录完成 |

V2 和 V3 在共享接口稳定后可作为独立工作包推进。它们的工程独立性不要求首期安排多个实现团队或建立多服务平台。

## 4. V0：先证明架构成立

只建设最小 Rust 核心、Kotlin 宿主和简单 Flutter 任务视图，以及电脑测试入口。最小交互包括提交、接收增量事件、执行一个工具、取消和查询结果。

验证内容：

- Android 和 Windows 使用同一核心源码，调用同一个人工模型服务样例并返回一致结果。
- Rust 请求 Kotlin 执行一个受控工具，结果正确返回 Rust；不依赖聊天页面上的控制器完成回调。
- 分批流式传输不会阻塞界面；取消后不继续派发工具动作。连续启动/取消至少 20 次，记录失败与资源释放情况。
- Activity 重建后可重新订阅已有任务；进程被终止后能够识别中断，不能假报持续运行。
- 模型凭据与任务文件由宿主注入，错误跨语言传递后仍能定位原因。
- 记录 Android 架构打包、调试、崩溃定位和增量构建的实际成本。

V0 的决定只有两种：验证通过，进入 V1；或记录无法接受的具体问题，收窄桥接方案/采用增量备选。V0 不通过时不继续大规模重写业务，也不为避免改变方案而同时堆叠多套桥接路径。

## 5. V1：Rust 核心与电脑 CLI

先接入一个实际选用的模型协议，完成文本流、一个文件读取工具、一个受控命令工具、取消、预算和任务记录。随后实现工具结果回送和结果核验。

Rust 核心拥有执行循环，电脑宿主注册文件/命令等能力，CLI 提交与查看任务。服务和 CLI 共用同一任务实现；工具执行结果作为证据，不以模型的“完成”文字代替测试或文件结果。

首轮验收用临时工程：定位一个问题、修改一个文件、执行测试并返回差异；另测命令失败、模型断流、超时、用户取消和结果不确定。第一版仅展示真实支持的工具与协议。四协议完整覆盖在 V4 验收，不能提前宣称等价于旧客户端。

任务存储使用普通状态记录与有序日志；已有任务身份可查询。命令执行需要管理本任务的进程树，且所有文件动作明确工作区范围。

在这个闭环上落实开发者能力：

- HTTP 和桌面 stdio MCP 各接入一个真实测试服务，验证工具发现、调用、资源和取消。
- 实现任务开始、工具前后、验收前和任务结束五个固定钩子点；验证阻止、超时和取消，不建设通用工作流引擎。
- 修改代码的任务默认使用独立 worktree 与分支；命令、文件工具和钩子绑定到实际工作区。两个任务互不覆盖，原工作区未提交改动保留。
- CLI 展示 Git 状态、差异、worktree 列表和文本提交图；使用系统 Git，验证原生 pre-commit 拒绝提交时如实报错。

手机图形视图在 V3 接入同一套仓库查询和操作接口，无需再实现第二套 Git 执行逻辑。

## 6. V2：Android 本机 Agent

Kotlin 宿主负责 Android 服务生命周期、权限和设备操作。Rust 核心使用统一工具接口请求观察、点击、输入、滚动、返回和启动应用；每个动作后取得新观察并核验效果。

原型先用两个自有演示 App 和三条完整任务，每条重复三次；停止后两秒内不再派发新动作。已提交给系统的动作不承诺撤销。权限撤销、窗口变化、控件失效、不可截图、回调迟到和服务重建应产生明确状态。

跨 App 能力的使用目的与发行渠道在本阶段确定。Google Play 对 Accessibility API 驱动的自主操作存在限制，见 [任务与设备文档的发布决策](../architecture/TASK-AND-DEVICE-CONTRACTS.md#9-发布决策)；技术原型通过不等于商店发布已获准。

## 7. V3：手机远程操作电脑

电脑宿主独立持有任务和模型配置，手机通过设备连接模块提交任务、订阅事件、查看差异与产物。首版在局域网或用户已配置的安全网络上验证，先完成任务本身；公网中继和自动穿透另行规划。

验收包括：

- 用户确认配对后校验设备身份与访问范围；撤销配对后旧凭据失效。
- 同一个提交标识返回同一个任务，提交超时后查询原任务。
- 手机离线五分钟，电脑继续按已接收目标执行；重连后获取同一任务记录与结果。
- 重复/缺失事件能够去重和补齐；日志中的暂时断连不会被解释成任务失败。
- 取消请求由电脑确认后才显示已停止；文件产物校验成功后才登记为已接收。
- 写操作结果未知时先核验，不自动重复提交。切换手机上选中的电脑不会改变正在执行任务的目标。
- 手机可查看目标电脑的 MCP 配置/能力、钩子结果与 worktree 任务关联；远程配置明确显示所属设备。
- 文件树展示暂存与未暂存变更，提交图展示分支、父节点、HEAD 和合并关系；基本暂存、取消暂存和审阅后提交可用。
- 手机重连不重跑钩子、不重建 worktree；外部 Git 操作后刷新到真实状态。

同一个 Rust 核心分别在手机和电脑运行，不以跨设备共享内存或共享数据库文件实现协作。

## 8. V4：产品功能与数据迁入

以用户工作区为单位迁入，而不是按所有页面、所有控制器、所有仓库分批复制。

建议顺序：会话与设置 → 资料/项目/记忆 → 语音 → 学习 → 创作 → 科研终端。顺序可以按实际使用频率调整，但每个模块都需要明确完成或明确暂不支持，不能默默丢失。

每个模块的迁移决定：

| 类别 | 处理 |
| --- | --- |
| 已有界面与交互仍适合 | 通过新任务客户端与业务接口接入，可复用组件 |
| 业务规则正确但耦合旧控制器 | 保留规则与用例，按新数据所有者重新实现 |
| 与新需求冲突的全局状态/执行逻辑 | 由新核心替代，不搬进新目录继续扩张 |
| 外部服务契约已稳定 | 继续复用服务与协议，如 Python 文档 MCP |

迁移验收覆盖：

- Rust 四协议与自动尝试规则、工具签名/图片往返、取消和限流/鉴权错误场景；统一样例比对行为，测试不照搬实现细节。
- 现有 MCP 配置与文档服务场景迁入；明确 HTTP/stdio 的执行设备和凭据归属。
- 代码工作区与项目/任务关联正确；包含分支与合并的测试仓库、浅克隆及按需加载历史时，Git 图与真实父节点和引用一致。
- 消息分支、项目关联、记忆作用域、生成版本、课程/作答/错题、角色/世界信息在导入后正确。
- 当前学习档案的 SharedPreferences 数据和 Markdown 记忆都计入迁移，不只导入 SQLite。
- v15/v16/v17 备份和素材字节校验通过；配置导入不把秘密写到普通任务日志。
- 新版本首次读取使用数据副本，迁移失败保留原始数据和明确错误。
- 长对话、流式输出、语音与文件任务在同设备、同构建模式下与旧版比较；根据实际基线设性能门槛，不承诺换 Rust 就自然变快。

## 9. V5：试用和版本切换

具备真实 Android 设备与 Windows 的安装、冷启动、停止、后台/前台、连接中断、任务恢复和数据回退记录后，再进入正式切换。原生二进制和 Kotlin 改动需要重新构建相应应用，不沿用只更新 Dart 的发布假设。

验证期采用独立数据目录。切换前导出并验证备份；回退使用事先保留的数据副本或明确兼容的导出，不让旧版本直接打开未知 V2 schema。

只有功能覆盖和兼容验收完成后才把 V2 设为默认入口。旧运行引擎与临时迁移适配在对应功能切换完成后退出，避免正式产品永久维护两套执行路径。

## 10. 本轮交付与下一项工作

本轮完成 V2 架构和实施计划，更新主文档入口，把原增量方案标为备选。未创建 V2 源码工程、移动现有源码或修改运行中的用户数据。

下一项实施工作为 **V0：Android 原生宿主 + Rust 共享核心 + 电脑入口的最小贯通验证**。这个验证通过后，才确定后续大规模迁移采用该架构。
