# 给 GPT 的提示词

下面两段可以直接复制使用。第一段用在第一次开工，第二段用在后续每个阶段。

---

## 一、首次开工

```text
你在 Expert Chat 仓库里工作。这是一个 Flutter 跨平台 LLM 客户端，状态管理用 Riverpod，界面是中文。任务是按已确认的设计方案改版界面。

【先读这些，按顺序】
1. design/REDESIGN-SPEC.md：改版规范，这是实现依据，务必完整读完。
2. design/feature-inventory.md：现有功能清单。改版后清单里的每一项都必须还能用到。
3. docs/PROJECT-PLAN.md 第 1、12、13 节：产品定位，以及之前的需求和验收记录格式。
4. 原型 design/expert-chat-redesign.html。可以用浏览器打开看交互，需要和 design/palettes.js、design/branding/ 放在一起。原型的回复和数据都是假的，只用来看交互和视觉，不要照抄它的 HTML 结构。原型和规范冲突时，以规范为准。

【硬约束，违反任何一条都算返工】
- 聊天和工作是两种独立会话：切换时新开会话，不给已有会话改类型，不转移授权，工作模式的底层行为不变（规范 §1.1）。
- 功能只改入口，不删。规范第 6 节以外的任何功能都不能删，也不能变成到不了的状态。
- 原有 14 套配色的色值不改；默认配色不替用户切换。
- 工作台拖动规则不变：默认 560，范围 340 到 min(可用宽度 − 430, 900)，可用宽度 < 820 时不停靠。
- 数据兼容：不改已有字段名；新增的偏好字段要进 UiPrefs 的 JSON、完整备份和配置迁移，旧数据缺字段时有默认值。
- 不新增依赖；确实需要时先说明理由并等我确认。
- 规范里标为 P2 的内容是新的后端能力，没有我的确认不要开工，也不要在界面上做"看起来能用但其实是假的"入口。
- 构建输出放到新的独立目录，不覆盖或停止正在运行的版本。

【工作方式】
1. 先只读调研，不改代码。对照规范和现有代码，给我一份 P0 的实施计划，内容包括：
   - 要改的文件和改法，每项都对应到规范的章节号；
   - 会受影响的现有测试；
   - 你发现规范和代码对不上的地方（规范写错的、代码已经变了的）；
   - 需要我拍板的问题。
   写完停下，等我确认。
2. 我确认后，实施 P0。只做 P0，不要顺手做 P1。
3. 自检：
   - flutter analyze 不能有新问题；
   - flutter test 全部通过；
   - 新改的界面补 widget 测试；
   - 加上规范 §4.13 要求的配色对比度测试（日辉 solar 按规范列为已知例外，不改它的色值）；
   - 在手机 360/390 宽、电脑 1280/1440 宽下，浅色和深色各截一次图，检查有没有溢出、截断或重叠。
4. 在 docs/PROJECT-PLAN.md 末尾追加一节，写明这一阶段做了什么、怎么验证的、还剩什么。
5. 汇报（格式见下），然后停下。

【遇到这些情况先问我，不要自己决定】
- 规范和现有代码的行为冲突。
- 要删除的东西涉及用户数据或存档格式。
- 要新增依赖，或者要改已有测试的断言（不包括因为文案、布局调整而必须更新的截图或选择器）。
- 某个功能在新结构里找不到合适的位置。

【汇报格式】
- 完成了哪些（对应规范章节号）；
- 改了哪些文件（每个文件一句话说明）；
- 验证结果：analyze 和 test 的实际输出摘要，截图检查结论；没跑的、失败的要明说，不要写成"应该没问题"；
- 和规范不一致的地方，以及原因；
- 遗留问题和下一步建议。

【提交】
是否提交、推送由我决定。需要提交时用仓库现有的 conventional commits 格式（feat: / fix: / docs: / refactor: / test:），正文写清改动和验证情况，不要加任何 AI 署名或"Generated with"之类的标识。
```

## 二、后续阶段（把 `<阶段>` 换成 P1 或 P2 的某一项）

```text
继续按 design/REDESIGN-SPEC.md 做 <阶段>，前一阶段已经确认通过。

要求和上一轮一样：先只读调研，给出这一阶段的实施计划（改哪些文件、对应规范哪一节、影响哪些测试、需要我拍板的问题），等我确认后再改；改完自检（flutter analyze、flutter test、补 widget 测试、手机和电脑在浅色和深色下截图检查），在 docs/PROJECT-PLAN.md 追加记录，按原格式汇报后停下。

这一阶段特别注意：
- P1：每移动一个入口，都要对照 design/feature-inventory.md 确认原来的功能还能找到；汇报时附一张"原入口 → 新入口"对照表。
- P2：每一项都是新的后端能力。先给我方案（数据结构、判定逻辑、存储和备份兼容、失败时怎么处理、要写哪些测试），我确认方案后再写代码。
```
