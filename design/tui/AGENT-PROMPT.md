## 1. 已知事实（开工前已核实）

- **代理循环在 Flutter 应用的状态层里**：ChatController 和 `lib/state/chat/`，基于 Riverpod。
- **设置和密钥依赖 Flutter 插件**：设置和 API 密钥存在 `flutter_secure_storage` 和 `shared_preferences` 里（见 `lib/data/settings_storage.dart`），会话存储依赖 `path_provider`。纯 Dart 命令行程序无法直接读取这些数据。
- **底层是纯 Dart**：`lib/domain/chat` 和 `lib/domain/llm` 基本不依赖 Flutter。
- **还没有会话级的对外接口**：`lib/domain/remote/remote_host.dart` 是远程工具执行主机，不负责会话。
- **开发机是 Windows**：主力终端是 Windows Terminal，Rust workspace 在 `next/`。

## 2. 推荐架构

先在阶段 0 核实，再决定是否采用。

```
Flutter 应用（GUI）
 └─ TUI 桥接服务（新增，Dart）
      · 只监听 127.0.0.1，随机端口，或使用 Windows 命名管道
      · 令牌写入只有当前用户可读的文件
      · 默认关闭：只有设置开关或启动参数 --tui-bridge 开启时才运行
      · 包装 ChatController 和 work_* 状态，不复制业务逻辑
          ▲
          │ WebSocket + JSON 消息（协议见 design/tui/PROTOCOL.md）
          ▼
Rust TUI（新增 crate：next/tui，二进制名 expert-tui）
      · ratatui + crossterm + unicode-width
      · 有两种数据源，实现同一个 trait：BridgeSource（真实后端）和 DemoSource（演示数据）
```

**选择这个架构的理由**：
- 不动现有后端，只新增代码。
- TUI 和 GUI 共用同一份状态，可以在 GUI 中定位同一个任务。
- 密钥继续使用现有的安全存储。
- Rust 的 TUI 生态最成熟，最容易按规格还原界面。

**什么时候换方案**：只有阶段 0 发现推荐方案不可行时才换，比如 ChatController 无法在不改动核心的情况下被外部驱动。换方案时，在 `ARCHITECTURE.md` 写明证据，选择改动面最小的替代方案。**禁止为了这个任务重构现有后端。**

## 3. 安全与边界（硬性规定）

- **桥接服务的权限**：
  - 只接受本机连接，必须校验令牌。
  - TUI 能做的事不能超过 GUI 的权限策略。切换到完全访问需要二次确认，规则与 GUI 相同。
  - 批准操作必须走现有的批准流程，不能绕过。
- **测试不能损坏用户的真实数据**：
  - 优先使用独立的数据目录或测试配置。
  - 如果必须使用真实配置，只新建标题以 `[TUI测试]` 开头的会话，不修改、不删除已有会话和设置。
- **真实模型调用**：
  - 只用于端到端冒烟测试。
  - 优先选择最便宜的可用模型。
  - 整晚累计不超过 30 次请求，次数记入日志。
  - 不允许把完全访问用于测试。
- **Git 规则**：
  - 开工时先运行 `git status`。工作区应该是干净的（用户已提交现有改动）。如果不干净，所有已有改动的文件一律不碰：需要修改它们时，把补丁写进 `design/tui/patches/`，并在日志里说明，由用户早上处理。
  - 新建分支：`git checkout -b feat/tui`。
  - 每个子任务完成并通过审查后提交一次。提交时只能用 `git add <具体路径>`，禁止 `git add -A`、`git add .` 和 `git commit -a`。
  - 提交信息不要加任何协作者署名或生成标识。
  - 不要 push，不要改写历史，不要删除不是本任务创建的文件。
- **改动范围**：
  - 只允许以下改动：新建 `next/tui/`，修改 `next/Cargo.toml` 的 workspace 成员列表，新建桥接服务相关的 Dart 文件，以及在应用启动处接入桥接服务所需的最少修改。
  - 其他现有文件如果需要修改，先在日志里写明理由，并且只做最小修改。

## 4. 阶段与分工

### 阶段 0：调研与契约（你亲自做，不交给子代理）

1. 读完 §0 的材料，确认推荐架构可行。在 `design/tui/ARCHITECTURE.md` 中写下：
   - 选定的方案
   - 桥接服务接入 ChatController 的具体位置
   - 规格中每个界面状态（`TUI-SPEC.md` §11）对应的后端状态来源

2. 写协议契约 `design/tui/PROTOCOL.md`，并写一份对应的 JSON Schema。至少包括：
   - **连接**：握手（协议版本、令牌）、心跳、断线重连后的状态快照
   - **请求**：
     - 会话：列出会话、打开会话、新建会话
     - 消息：发送消息、运行中补充要求（排队）、撤回排队内容、中断任务
     - 批准：允许一次、本会话允许、拒绝、拒绝并说明
     - 设置：模型与思考强度、权限模式、工作模式 / 计划模式、执行位置（运行中拒绝）
     - 改动：获取改动列表与差异、验收、要求修改
   - **事件**：
     - 轮次开始和结束（含轮次计数）
     - 助手文本增量、思考开始和结束
     - 步骤开始、更新（输出尾部）、结束（结果和元信息：+/− 行数、耗时、退出码）
     - 子代理状态
     - 批准请求、改动摘要
     - 请求重试（错误码、倒计时、第几次）、最终错误
     - 上下文用量
   - **启动页所需信息**：版本、工作区、git 分支和未提交改动数、已加载的上下文、最近会话
3. 根据真实后端的行为，录制或编写夹具事件流，至少覆盖规格中的每个画面：运行中、等待批准、待验收、失败与重试、多个子代理。把它们放在 `design/tui/fixtures/*.jsonl`。Rust 的 DemoSource 和 Dart 桥接服务的契约测试都使用这批夹具。

**阶段 0 完成前，不要派出写实现的子代理。** 协议定下来之后，修改它必须由你批准，并同步更新两端。

## 6. 你如何管理子代理

- **派任务时写清楚**：目标、负责的文件、不能碰的文件、参考的规格章节、完成标准、必须运行的测试命令。子代理看不到你的上下文，任务说明是它唯一的信息来源。
- **审查不能只看子代理的报告**：要亲自看 diff、亲自运行测试和快照，再与规格逐条对照。不合格就退回，并具体指出哪里不对。
- **限制重试次数**：同一个问题最多让子代理修复 3 轮。仍然没解决就标记为「阻塞」，写进日志，转去做其他部分，不要卡住整体进度。
- **线与线之间的依赖只通过 PROTOCOL.md 和夹具**：不允许子代理为了自己方便修改对方负责的代码。
- **规格没写清楚的地方**由你统一决定，并告知所有相关子代理，避免两边各自理解不同。
