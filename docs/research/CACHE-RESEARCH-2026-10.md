# 缓存命中研究更新

检索截至 2026-10-22。三个研究代理分别查找 API 缓存与压缩、服务端 KV 管理、上下文排序，合并时核对论文版本、正文实验条件和作者仓库。本文补充 [电脑 Agent 调研](DESKTOP-AGENT-RUNTIME.md)，不替代 [项目主规划](../PROJECT-PLAN.md)。

**对当前第三方模型 API 客户端，优先验证稳定前缀、一次压缩后复用，以及可交换资料块的排序。服务端 KV 淘汰、预取和近似拼接留给自部署模型阶段。** 本轮找到并核验的直接相关新工作包括 2026 年 10 月论文；不把检索结果视为领域完整清单。

## 1. 近期重点论文

| 论文及核验版本 | 核心贡献 | 对本项目的意义与边界 |
| --- | --- | --- |
| [Request Order Matters](https://arxiv.org/html/2610.05833v1)，2026-10-05，v1 | 滚动文档窗口中的非前缀 KV 近似复用，可能受之前处理过的请求影响；比较 token 与文档连续区域的选择性重算 | 为自部署近似复用增加顺序敏感性测试。实验关闭 vLLM 精确前缀缓存，不能推导出普通精确缓存改变答案 |
| [Tessera](https://arxiv.org/abs/2609.32999v1)，2026-09-26，v1 | 用检索需求协调 KV 组合、驻留、远端获取与请求路由 | 自部署方向；客户端不能借一个请求参数获得该机制 |
| [KVSET](https://arxiv.org/abs/2609.27746v1)，2026-09-23，v1 | 根据请求轨迹估计不同 LRU 缓存容量下的命中曲线 | 是容量规划工具，不是自动提高命中的客户端算法；需要自己的推理服务轨迹 |
| [Prefix Sharing Is a Sorting Problem](https://arxiv.org/html/2609.13692v1)，2026-09-12，v1 | 通过请求聚类与上下文块排序增加前缀共享 | 有作者复现代码，适合做实验；论文只测预填充 token 成本，没有实际服务延迟或回答质量评测 |
| [CacheWeaver](https://arxiv.org/html/2606.19667v2)，首发 2026-06-18，修订 2026-09-04，v2 | 在证据集合不变的条件下，按历史前缀树贪婪排列证据 | 应用层可借鉴；主要效果来自具有时间局部性的合成突发轨迹，不能保证编码任务同样获益 |
| [ReCache](https://arxiv.org/html/2608.19662v1)，2026-08-20，v1 | 独立编码工具/技能资源，配合注意力、位置及裁剪设计复用 KV | 有代码，但需要改模型与训练；内存节省不等于第三方 API 费用下降，完整裁剪也不是无损 |
| [Cache-Aware Prompt Compression，CAPC](https://arxiv.org/html/2607.15516v1)，2026-07-17，v1 | 稳定内容先做与查询无关的压缩，然后缓存固定压缩版本 | 与当前 API 客户端最直接相关；具体阈值来自 Sonnet 4.6 和单一 TTL 的观测，不作为跨模型常量 |

以上按核验到的 arXiv 版本讨论，数字是作者实验结果，不是 Expert Chat 的实测收益。

## 2. 最值得用于客户端的三项研究

### 前缀排序

Prefix Sharing 在 BEIR/BM25 轨迹上报告约 17%–36% 的预填充 token 成本下降。这个量不能写成响应时间减少或 API 账单同比下降。正文明确没有做生成质量实验；更大重排窗口还需要批处理或等待。[论文方法与限制](https://arxiv.org/html/2609.13692v1)。

作者提供 [求解器、理论验证和检索轨迹脚本](https://github.com/Darrenus/prefix-sharing-is-sorting)。它是研究代码，不是可以直接替换现有模型层的 Agent SDK。

工程选择：只在**新构建且语义可交换的资料块**上比较排序；保留必要相关性顺序和稳定引用标识。初始使用不等待未来请求的在线策略。已有对话、工具调用与结果的因果顺序、运行中任务的工具 schema 不逐轮重排。

同样一组资料出现在不同对话后部，并不自动形成相同前缀。实验必须检查实际请求中从开头到资料块之前的内容是否也一致，不能仅统计资料集合重合率。

### 历史证据顺序

CacheWeaver 的 v2 在三组 vLLM 配置下报告中位首字延迟约下降 20%–33%；主要轨迹为合成突发请求，公开问答检查仅覆盖固定样本切片。效果依赖资料重叠和时间局部性，论文也承认顺序变化可能影响位置敏感任务。[论文实验与局限](https://arxiv.org/html/2606.19667v2)。

工程选择：先与简单稳定排序比较，只有真实编码任务获得成本/延迟收益且质量不下降，才增加历史前缀树。对于外部 API，客户端历史只是复用机会的线索，不代表服务端仍保存着对应 KV。

### 先压缩再缓存

CAPC 将固定资料压缩一次后复用，避免每个问题生成不同的压缩前缀。它的约 3,500 token 分界及命中曲线仅是单模型、5 分钟 TTL 的观测，不是厂商保证。LongBench-v2 的约 49% 相对 cache-only 均值节省，与零售任务上的约 8.5% 是不同实验；相同的 36/50 成功数不能证明质量等价。[论文及局限](https://arxiv.org/html/2607.15516v1)。

工程选择：增加“原始稳定资料”和“一次压缩后冻结的资料”对照组。压缩对象优先是冗长说明与可回查参考资料；用户硬性约束、工具参数 schema、签名和协议字段保持完整。资料版本改变时重新生成对应压缩版本，不能为缓存保留旧事实。

## 3. 服务端研究能带来什么

Request Order Matters 使用 Qwen3-8B 和 LMCache/vLLM 的非前缀近似复用，在固定 5% 重算预算下，文档对齐重算比 token top-k 对请求顺序更稳，但仍没有恢复到完全一致。其测试是滚动窗口中的字段提取，不是完整编码任务。[实验设置与结果](https://arxiv.org/html/2610.05833v1)。

由此应增加的验证是：相同目标请求分别在冷缓存、不同预热历史、跨会话交错后执行，比较结果与完整重算基线。只有采用近似 KV 复用时才需要把该风险归入产品；标准精确前缀缓存与它不同。

KVSET 提供 [作者容量估计实现](https://github.com/llc-kc/kv_cache_capacity_estimator)，以 LRU 为假设评估工作集；论文用内部编码 Agent 请求轨迹验证。若以后自部署推理，这比自行编写一套容量模拟器更值得先试；它不能推测商业 API 未公开的淘汰和路由策略。[论文](https://arxiv.org/pdf/2609.27746)。

Tessera 将检索信息用于分布式 KV 管理，报告特定负载下最高 3.6 倍平均首字延迟改善；需要控制推理与 KV 组合策略。ReCache 的 [作者实现](https://github.com/EIT-NLP/ReCache) 涉及训练与注意力修改，完整裁剪下存在质量损失。两者先列为自部署候选，不加入当前客户端的必做依赖。[Tessera](https://arxiv.org/abs/2609.32999v1)、[ReCache](https://arxiv.org/html/2608.19662v1)。

## 5. 应谨慎使用的补充证据

- [Don’t Break the Cache](https://arxiv.org/html/2601.06007v2)：首发 2026-01-09，当前 v2 为 01-31。是供应商策略对照的重要早期实测，但以研究任务和较长系统提示为主。搜索索引旧数字与 v2 不同；实验中用于破坏缓存的 UUID 不能成为生产配置，也不能推导出所有模型都应丢弃工具结果。
- [CacheScout](https://arxiv.org/abs/2608.14624)：在线学习代理执行转移以指导淘汰与预取，需改推理服务。页面与正文标注 2026-07-16，但编号为 2608.14624，日期元数据存在不一致，未擅自改为 8 月。本轮未确认作者实现，不照搬成额外付费 API 预热请求。
- [Models Take Notes at Prefill](https://arxiv.org/abs/2606.17107)：2026-06-14，研究追加更正与 KV 编辑/组合。其显著延迟倍率来自特定可变字段与负载条件，不能外推为日常编码收益。追加更正可单独测试，但仍要确认模型不受过期状态误导。

## 6. 对 Expert Chat 实验计划的补充

| 优先级 | 实验组 | 判定依据 |
| --- | --- | --- |
| 先完成 | 固定核心提示、稳定工具序列化、动态信息追加 | 每轮实际 cache read/write、总费用与前缀首次变化点 |
| 第一轮比较 | 原始稳定资料 / 一次压缩后冻结的资料 | 同等任务质量下的费用、延迟与再读取次数 |
| 第一轮比较 | 相关性顺序 / 稳定顺序 / 历史前缀感知顺序 | 仅处理可交换资料；记录实际首字延迟与任务完成率 |
| 随子代理验证 | 精简交接 / 公共前缀复用 / 全历史分叉 | 总任务费用、完成时间与重复工作；不把缓存 token 当免费 |
| 自部署后再做 | 容量曲线、淘汰/预取、非前缀 KV 组合 | 实际引擎命中、吞吐、排队、质量与请求顺序敏感性 |

区分请求命中率、输入 token 加权命中率、可复用前缀比例和实际费用节省。冷热缓存、模型/端点、并发、请求间隔及压缩开销分别记录，避免将一次冷启动或不同负载误当作算法效果。

本轮结论是加入可复用方案的比较实验，而不是将论文的模型、阈值或宣传数字直接写进产品。实施仍按主规划的阶段 1–2 推进。
